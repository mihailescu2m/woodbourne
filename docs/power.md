# Power / Standby — what we tried and why it failed

This is the autopsy of the project: every approach to stopping the 20‑minute idle
standby *from inside the DMP firmware*, and the reason each one didn't hold. The short
version is at the top; the long version — dozens of builds across several months — is
below.

---

## TL;DR — the root cause

**The standby is host‑driven.** The Woodbourne has two processors:

- the **DMP** (BridgeCo ARM926EJ‑S) that runs the application firmware we patch, and
- a **host companion chip** (`CommunicationSettings/HostController = SPI`, DM1000‑class)
  that owns power, the front panel, and — crucially — the **20‑minute idle timer**.

When the host's idle timer expires it tells the DMP to tear down audio (the AirPlay
"Apple Stop" sequence, driven by injected EVkCmd `0xDE`/`0xDF`/`0xE1`) and then drops
the system into standby. The DMP is a *follower* here. Nothing the DMP does to the
teardown changes the host's decision — the host keeps its own clock and will re‑issue
the command or simply cut power.

That single fact invalidates the entire "find the timer / block the transition" family
of fixes. The only DMP‑side action that resets the host's clock is a **real reboot** —
which is exactly what the shipped [keepalive patch](patch-2-keepalive-reboot.md) does.

## Things we tried (and why they didn't work)

### 1. NapManager / NAP state blocking
**Idea:** AirPlay stop walks the NAP state machine `0 → 1 → 7 → 5`; `NapState 5`
switches the UI to StandbyMode and `NapState 7` "arms the standby timer". Redirect those
entries in `UIDefaultModeHandler::notifyNapStatusChanged`'s jump table (file `0x0682AC`)
to the no‑op handler.

**Result:** Failed (both "state 5 only" and "state 5 + 7"). The NAP handler is a
*consequence observer*, not the cause — it reacts to the standby that the host already
decided. The EVkCmd `0xDE→0xE1→0xDF` chain and Apple Stop are generated by code that
never goes through this jump table. We were muting the messenger.

### 2. PowerManager.cpp — `doSetSystemPowerState` guard
**Idea:** All power transitions funnel through `PowerManager::doSetSystemPowerState`
(Thumb, `0x08DE30`). Add a guard that allows "on" states (1, 5–8) and silently discards
transitions to standby/sleep (0, 2, 3, 4).

**Result:** Failed. The guard did discard the DMP's own transition request, but the
speaker still went to standby — the host powered the system down independently of the
DMP's PowerManager. Variants ("Path B redirect", blocking specific target states) all
behaved the same. (An over‑aggressive version that NOP'd the state‑0 BEQ in the power
transition function `0x1E1634` **bricked** the speaker until a full capacitor‑discharge
power cycle — state‑0 init is required during boot.)

### 3. Apple Stop / EVkCmd dispatcher NOPs
**Idea:** Kill the teardown at its source — NOP the EVkCmd `0xDF` power‑down branch in
the dispatcher (`0x46F838`), NOP the standby call `bl 0x347FEC` (`0x329884`), or NOP the
`BLX 0x1E1174` inside the Apple Stop function (`0x018508`).

**Result:**
- `0xDF` NOP and the `bl 0x347FEC` NOP were each insufficient — Apple Stop fired through
  a parallel path and the host still pulled the plug.
- The Apple Stop `BLX` NOP *did* block idle standby — but it also **broke BL‑mode
  reboot**, because the web‑UI bootloader entry uses the *same* Apple Stop function.
  Since there is no confirmed hardware BL‑entry button, this was a brick risk and was
  abandoned.
- NOP‑ing EVkCmd `0xDE` ("stop source") broke **source switching** (AirPlay → Bluetooth)
  — `0xDE` is not standby‑specific.

### 4. Hunting for the "20‑minute timer"
**Idea:** Find the timer registration that fires at 1200 s and disable it.

**Result:** Dead end — there is no such timer *in the DMP*. We searched for WFI callers,
sleep paths, idle‑timer setups, and traced the standby call graph
(`analyze_sleep.py`, `find_sleep_paths.py`, `find_wfi_callers.py`, `analyze_standby*.py`,
`psm_standby_trace.txt`). Every candidate was downstream of the host signal. The 1200 s
clock lives on the companion chip, which we cannot disassemble.

### 5. Config / RSDB defaults
**Idea:** Flip configuration defaults — `EnableSleepTimer = 0` (`0x4FE6F5`), PSM
settings, idle thresholds — so standby is disabled by policy.

**Result:** Failed. The defaults either had no effect on the host's timer, or were
overridden by persistent NVRAM. The host doesn't consult these DMP‑side keys for its
idle decision.

### 6. Injected EVkCmds / "tell the host what to do"
**Idea:** On receiving the standby EVkCmds, inject a `writeToHost` to either stop the
standby or command a host reboot instead — e.g. `writeHostReg(0x27,0)` ("Sending control
to host"), `reg write 17/25`, the RemoteCommand register (`reg write 64 ...`), or an AVR
init.

**Result:** Failed to *prevent* standby. We could make the device hand control to the
host (that's the BL path), but we never found a host register write that says "don't
standby" or "reset your idle timer". `reg write 64 bytes 3 1 1 2` had no effect; holding
reg 227, polling reg 64, etc. all left the host timer running. Empirically confirmed
many times: **only an actual soft reboot resets the host clock.** This is what pointed us
to the keepalive‑reboot design.

### 7. Audio‑state detection
A useful *positive* result rather than a failure: we needed the keepalive to skip
rebooting during playback. `AirTunesPlaybackStatus` only covers AirPlay; the general
`audioStatus()` (`0x205730`, returns 1 when the NAP state is "playing") covers AirPlay,
Bluetooth, AUX and other inputs. That function is what the shipped cave uses.

### 8. Runtime patching via telnet
**Idea:** Just `wr` the fix into code memory live over the telnet shell.

**Result:** Blocked by the MMU — code pages are mapped read‑only/execute; `wr` to a code
address returns "access denied by MMU". All fixes must be baked into the flashed image.

### 9. External RPi keepalive daemon
**Idea:** Skip the firmware entirely. Run a Raspberry Pi Zero 2 W on the LAN that pokes
the speaker awake (a brief silent AirPlay burst, or a `sys reboot` over telnet when
standby is detected).

**Result:** Worked partially, then failed in practice — RAOP sinks went stale, the
GoAhead web server had limited slots, and the reboot‑on‑detection was racy (standby had
often already begun). It also required an always‑on extra device. Full code and a longer
post‑mortem are in [keepalive.md](keepalive.md). This experiment is what finally
convinced us the *reboot* is the only reliable lever — so we moved it inside the
firmware, where it became Patch 2.

## The one thing that worked

Pre‑empt the host instead of fighting it: a self‑hosted idle timer inside the DMP that
performs a clean `setSystemPowerState({3,6})` soft reboot a few minutes before the host
would standby, skipping reboots while audio plays. The host re‑initialises and restarts
its 20‑minute clock from zero every cycle, so deep standby is never reached — and because
the reboot path is separate from the bootloader handoff, BL‑mode reflashing still works.

See [Patch 2: Idle Keepalive](patch-2-keepalive-reboot.md).
